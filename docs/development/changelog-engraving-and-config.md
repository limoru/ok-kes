# 改动记录：存档主战员保护、任务优先级分层、配置导入预览、装备词典与刻印功能

本文档记录对项目所做的全部代码改动，按功能模块分节说明，每节包含
需求背景、涉及文件、具体改动内容。

---

## 1. 刷存档主战员未匹配时自动停止并清空缓存

### 背景
卡厄思模式进入信息统计页面识别刷存档主战员时，如果三名出战主战员都没有命中
配置的目标名字（通常是因为没有手动把该角色配到出战队伍里），旧逻辑会继续
运行，导致后续装备分配、卡牌复制等功能全部因为找不到目标主战员而失效，用户
往往要等一整局跑完才发现配队错了，浪费时间。

### 改动内容
文件：`ok_tasks/utils_chaos.py`

- 新增 `_TARGET_MEMBER_FEATURE_NAMES` 常量，列出全部 6 个刷存档主战员相关的
  运行时特征名（`target_member`、`target_member_small`、
  `target_member_in_select_card`、`target_member_tiny`、
  `target_member_in_mask_card`、`target_member_large`）。
- 新增 `_clear_target_member_features(task)` 函数：清空内存中的
  `feature_set.feature_dict` / `feature_set.box_dict` 缓存，并删除磁盘上对应
  的 `.png` 特征图片文件。
- 修改 `handle_archive_target_member`：当三名主战员均未命中配置的目标名字时，
  调用 `_clear_target_member_features` 清空缓存，将 `save_target_member` 标记
  重置为 `False`，并调用 `task.disable()` 停止卡厄思模式任务，不再继续运行。

### 效果
配队错误时立即停止并给出日志提示，避免继续浪费时间空跑。

## 2. 事件任务优先级分层：新增"必选任务优先级"（第一优先级）

### 背景
原有的事件任务选择顺序是"先拉黑过滤，再匹配任务优先级"。这导致一种情况无法
处理：某个选项同时命中"任务优先级"关键词（如"复制"）和"拉黑任务"关键词
（如"咒术卡牌"），会被拉黑过滤直接排除，即使这个选项本质上是用户想要的
（例如"复制一张卡牌，可以接受获得一个咒术卡"）。

用户需求：新增一个优先级更高的判断层，命中即直接选择，完全无视拉黑过滤。

### 改动内容
文件：`ok_tasks/utils.py`（函数 `handle_event_task`）

原来的判断顺序：
```
拉黑过滤 -> 任务优先级匹配（含装备优先级）-> attack_event 兜底 -> 随机选择
```

调整为三级结构：
```
第一级：必选任务优先级匹配（忽略拉黑过滤）
  -> 命中则直接选中，流程结束
第二级：拉黑任务过滤（仅在第一级未命中时执行）
第三级：任务优先级 + 装备优先级匹配（在拉黑过滤后的选项中匹配）
  -> attack_event 兜底 -> 随机选择
```

文件：`ok_tasks/ChaosMode.py`

- 新增配置项 `必选任务优先级`（列表，默认 `["复制"]`）。
- 新增对应的 `config_description` 说明文字。

> 注：`ok_tasks/SortieMode.py`（出击模式）**不需要**此功能，未添加对应配置项。

### 效果
即使某个事件选项同时带有负面效果关键词（如"咒术"、"压力"），只要命中"必选
任务优先级"里的关键词（如"复制"），也会被直接选中，不会被拉黑过滤误伤。

## 3. 配置导入前增加预览确认弹窗，并支持一键备份当前配置

### 背景
点击"导入配置码"后，粘贴编码会立即覆盖当前全部配置，没有确认环节，用户
误操作后无法恢复被覆盖的配置。

### 改动内容
文件：`ok_tasks/config_io.py`

- 将原来的 `_import_config_from_text`（解码 + 校验 + 直接写入）拆分为两步：
  - `_decode_and_sanitize_config(task, encoded_text)`：只做 base64 解码和按
    `default_config` 校验字段，不写入。返回 `(sanitized_data, ignored_keys)`。
  - `_write_sanitized_config(task, data)`：只做写入配置文件和刷新
    `task.config` 缓存。
  - `_import_config_from_text` 保留下来，内部调用上述两步，继续供"热门配置
    应用"、"本地方案加载"等不需要预览的场景复用。
- 新增 `_format_config_value(value)`：将配置值格式化为便于阅读的字符串
  （布尔值转"开启/关闭"，列表转用"、"连接的文本等）。
- 新增 `_save_current_config_as_profile(task, mode, parent=None)`：从原
  `make_save_local_config_callback` 中提取出的公共保存逻辑，支持传入父窗口
  （用于嵌套对话框场景）。
- 新增 `_show_import_preview_dialog(task, mode, sanitized_data, ignored_keys)`：
  展示导入预览对话框，逐项列出"当前值 → 导入后的值"（值相同的字段不列出），
  并提供"备份当前配置"按钮（调用 `_save_current_config_as_profile`）、"取消"
  按钮、"确认导入并覆盖"按钮。返回用户是否确认导入。
- 修改 `make_import_callback(task, mode)`：新增 `mode` 参数。粘贴编码后先
  调用 `_decode_and_sanitize_config` 解码校验，再调用
  `_show_import_preview_dialog` 展示预览，用户确认后才调用
  `_write_sanitized_config` 真正写入。
- 简化 `make_save_local_config_callback`：直接复用
  `_save_current_config_as_profile`，去除重复的命名/覆盖确认逻辑。

文件：`ok_tasks/ChaosMode.py`、`ok_tasks/SortieMode.py`

- 更新 `make_import_callback` 调用处，分别传入 `'chaos'` / `'sortie'` 作为
  `mode` 参数。

### 效果
导入配置码前会先看到一份差异预览，可以在确认导入之前先备份当前配置，取消
则不会产生任何改动。

## 4. 装备词典（equipment_dictionary.json）

### 背景
为后续功能（装备位识别增强、分享配置码压缩）做准备，需要一份"装备名称
<-> 所属位"的固定映射表。

### 改动内容
新文件：`ok_tasks/assets/equipment_dictionary.json`

- 数据结构：
  ```json
  {
    "version": 1,
    "slots": {"0": "攻击力", "1": "防御力", "2": "生命值"},
    "slot_id_ranges": {"0": [0, 999], "1": [1000, 1999], "2": [2000, 2999]},
    "equipments": [
      {"id": 0, "name": "蚀化臂铠", "name_zh_tw": "", "slot": 0},
      {"id": 1000, "name": "拷问工具箱", "name_zh_tw": "", "slot": 1},
      {"id": 2000, "name": "异象石碑", "name_zh_tw": "", "slot": 2}
    ]
  }
  ```
- **id 分段规则**：按位置分段，每段预留 1000 个编号（1号位/攻击力位置
  0~999，2号位/防御力位置 1000~1999，3号位/生命值位置 2000~2999），只是为了
  方便人工管理时一看编号就知道所属位置，不影响未来接入分享码压缩时的实际
  编码长度（压缩时按"位置内实际收录数量"计算最小位数，不会直接搬运十进制
  id 本身）。
- **name_zh_tw 字段**：繁体名称占位字段，暂未启用繁体识别支持，统一留空
  字符串；后续启用时直接在此字段补充繁体名，不需要改动数据结构。
- **维护规则**（写在文件内 `_readme` 字段中）：
  1. 新增装备只能使用一个从未用过的新 id（在所属位置区间内选取）。
  2. 已存在的 id 一旦被使用过，永远不能删除、不能改指向别的装备名称、不能
     与其他条目交换 id（否则会破坏已分享出去的配置码）。
  3. 允许修正已存在条目的 `name`/`name_zh_tw` 拼写错误或补充/修正 `slot`
     值，但 `id` 本身不能变。

文件：`ok_tasks/utils.py`

- 新增模块级缓存 `_EQUIPMENT_DICTIONARY_CACHE`（懒加载，首次用到时读盘一次，
  之后复用缓存，不重复读取）。
- 新增 `_load_equipment_dictionary()`：加载并解析词典文件，返回
  `{"by_id": {...}, "by_name": {...}}` 结构。文件缺失或格式错误时返回空
  结构，不影响主流程运行。
- 新增查询接口：
  - `get_equipment_id(name)`：按装备名称查询词典编号。
  - `get_equipment_name(equipment_id)`：按编号查询装备名称。
  - `get_equipment_slot_by_name(name)`：按装备名称查询所属位置下标。
- 新增 `_equipment_slot_by_dictionary(ocr_name)`：按装备词典用双向包含匹配
  OCR 名称，返回词典记录的位置下标。
- 修改 `_equipment_info`：位置判定优先查装备词典（按名称直接确定，不受 OCR
  类型文本漏识别影响），词典未收录该装备时才回退到原有的"识别类型文本"
  逻辑。

### 效果
装备识别不再完全依赖"类型文本"这一行 OCR 结果，只要装备名在词典里，即使
类型文本行漏识别，也能正确判定位置，提升装备识别稳定性。

## 5. 装备刻印功能（卡厄思模式）

### 背景
卡厄思模式部分地图商店/战利品中的装备会带有随机刻印词条（写在装备描述
文字里）。原有逻辑只按装备名称的优先级+品质购买/安装装备，完全不识别刻印
词条，无法满足"刷指定刻印"的需求。

### 需求确认要点（经过多轮讨论确认的最终规则）
1. 刻印词条就在现有的装备描述区域内，不需要新增截图区域，直接复用已有的
   OCR 结果。
2. 整个游戏只有一套通用刻印目标，不区分 1/2/3 号位置；玩家可配置多个可接受
   的刻印关键词，命中任意一个即算满足。
3. 目标装备名沿用现有的"装备 X 号位优先级"配置。
4. 装备名和刻印的"完成"判定是相互独立的两个维度：某位置只有"当前装备名
   命中目标名列表" **且** "当前描述命中任一目标刻印关键词"同时成立，才算
   该位置"已完成"。
5. 刻印可以通过"无刻印装备覆盖有刻印装备"的方式继承保留；反之，用带有
   （其他）刻印的装备覆盖会让原刻印丢失。
6. 装备分配决策标准从"名字优先级+品质比较"整体切换为"该候选装备是否能让
   位置在目标名+目标刻印上产生进展"：
   - 位置已完成 -> 任何候选都拒绝。
   - 候选带目标刻印，位置当前没有目标刻印 -> 接受（无论候选叫什么名字，
     优先占住刻印）。
   - 候选带目标刻印，位置已有目标刻印但候选不是目标名 -> 拒绝（没有新
     进展）。
   - 候选带目标刻印，且候选正好是目标名 -> 接受（一步到位）。
   - 候选不带任何目标刻印，但候选是目标装备名，且位置尚未完成 -> 接受
     （继承机制保留原有刻印，同时换上目标名字）。
   - 其余情况（候选既不是目标名，也不带目标刻印） -> 拒绝。
7. 不满足上述"接受"条件的候选装备，一律不分配给目标主战员，转由其他队员
   随机接收（游戏点击本身会自动覆盖对方原有装备，不需要额外处理）；目标
   主战员被排除在候选池之外，不会被随机点中。
8. 商店购买场景新增信用点保护：低于设定阈值时不评估购买，直接取消（避免
   为了追刻印超支）；白拿装备场景不受此限制（不花钱）。
9. 商店购买页面和白拿装备页面使用同一套判定函数，不做差异化处理。
10. 该功能只在卡厄思模式实现，出击模式不涉及。

### 改动内容

新文件：`ok_tasks/utils_equipment_engraving.py`

纯逻辑判定模块，不依赖 `ok` 框架、不做任何截图/OCR/点击操作：

- `has_target_engraving(description, engraving_keywords)`：判断装备描述
  文字是否命中目标刻印关键词列表中的任意一个。
- `matches_target_name(name, target_names)`：判断装备名是否命中目标名列表
  中的任意一个（双向包含匹配，与项目内 `_match_equipment_name` 的匹配规则
  保持一致）。
- `is_slot_completed(current_name, current_description, target_names, engraving_keywords)`：
  判断某位置当前是否已"完成"（目标名+目标刻印同时满足）。
- `should_assign_to_target_member(current_name, current_description, candidate_name, candidate_description, target_names, engraving_keywords)`：
  核心判定函数，返回 `(是否分配给目标主战员, 判定原因说明)`，原因说明用于
  日志打印。

已用 6 组场景手工验证全部分支行为符合设计（位置已完成拒绝一切候选、候选带
刻印占住空位置、位置有刻印后候选名字不对被拒绝、位置有刻印且候选是目标名
被接受、候选不带刻印但是目标名通过继承被接受、候选两项都不满足被拒绝），
全部通过。

文件：`ok_tasks/ChaosMode.py`

新增三个配置项：
- `刷装备刻印`（布尔，默认 `False`）：功能总开关。
- `装备刻印优先级`（列表，默认 `[]`）：目标刻印关键词，不区分位置，命中
  任意一项即满足。
- `刷装备刻印信用点下限`（数字，默认 `0`）：商店购买时，当前信用点低于该
  值则跳过购买评估；设为 0 表示不限制。仅影响商店购买，不影响免费获得的
  装备。

并为以上三项添加了 `config_description` 说明文字。

文件：`ok_tasks/utils.py`

- 顶部新增 `from utils_equipment_engraving import should_assign_to_target_member`。
- `handle_equipment` 函数改动两处：
  1. 购买装备页面价格检查之后，新增信用点下限检查：若 `刷装备刻印` 开启且
     `刷装备刻印信用点下限` 大于 0 且当前信用点低于该值，直接点击"取消"，
     不继续评估购买。
  2. 原来计算 `should_install_first`/`install_reason` 的位置，用
     `if _get_config_value(task, "刷装备刻印", False):` 分支：
     - **开启时**：读取 `装备刻印优先级` 配置，调用
       `should_assign_to_target_member` 判定，不再调用
       `_should_install_equipment`，也不做"传说装备互斥"判断。
     - **关闭时（默认）**：完全保留原有代码逻辑，逐字不变（`_should_install_equipment`
       比较 + 传说装备互斥判断），确保未开启此功能的用户行为不受任何影响。

  `preferred_member_index`（决定谁是目标主战员）和 `other_members`（过滤掉
  目标主战员后的候选队友列表）两个变量的计算逻辑未改动，"不满足刻印条件
  时目标主战员被排除、只在其余队员中随机分配"这条规则通过既有的过滤逻辑
  自然实现，不需要额外代码。

### 效果
开启"刷装备刻印"后，装备分配完全按"是否推进目标名+目标刻印进展"决策，
不满足条件的装备一律转给其他队员，不会误分配给目标主战员，也不会因为旧的
优先级/品质比较逻辑而误换掉已经锁定的完美刻印装备。关闭开关（默认状态）
时，行为与改动前完全一致。
